这些概念是并发编程（Concurrent Programming）中最基础、也最容易混淆的一组概念。

最重要的是：同步/异步、阻塞/非阻塞、单线程/多线程、并发/并行、协程，实际上描述的是不同维度的问题。它们并不是一组互相排斥的概念。

例如，完全可以存在：

- 单线程 + 异步 + 非阻塞 + 并发
- 多线程 + 同步 + 阻塞 + 并行
- 单线程 + 协程 + 同步 + 阻塞
- 多线程 + 协程 + 异步 + 并行

下面从最基本的概念开始，建立一个完整的知识体系。

## 一、先建立整体框架

我们可以把这些术语划分为六个维度。

| 维度   | 主要概念    | 回答的问题        |
| ---- | ------- | ------------ |
| 执行资源 | 单线程、多线程、进程、GPU 队列 | 谁实际执行指令？ |
| 任务时间关系 | 并发、并行 | 任务是否交叠，是否同时运行？ |
| 完成语义 | 同步、异步 | 结果何时交付给调用者？ |
| 等待与进展 | 阻塞、非阻塞 | 当前执行资源是否因等待而停住？ |
| 控制流表达 | 普通函数、协程、状态机 | 执行过程能否保存状态并恢复？ |
| 调度权限 | 抢占式、协作式 | 谁决定何时切换执行？ |

理解这六个维度以后，你就不容易把它们混为一谈。

这六个维度是为了建立工程直觉的教学框架，不是严格互斥且完备的并发理论公理。特别要区分三点：同步 API 和 mutex 等同步原语属于不同语境；协程是控制流抽象，不是线程；多线程只提供并行机会，不保证已经发生物理并行。

数据共享、消息传递、锁、原子操作和内存可见性是贯穿这些维度的横切问题。它们决定并发程序是否正确，但不需要被强行塞进上面的六个分类轴。

## 二、线程（Thread）是什么？

### 2.1 先理解程序、进程和线程

先建立三个概念：

- 程序（Program）：存储在磁盘上的代码与相关数据。
- 进程（Process）：程序运行时形成的执行环境，拥有虚拟地址空间等资源。
- 线程（Thread）：进程内部的一条执行流，是操作系统调度 CPU 执行代码的重要单位。

可以简单理解为：

Process（进程）

共享的地址空间和进程资源

Thread 1

独立执行流

Thread 2

独立执行流

Thread 3

独立执行流

同一进程中的线程通常共享堆内存等资源，但有各自的调用栈、寄存器执行状态。

线程最重要的特征是：它有自己的执行位置和调用栈。

例如：

```cpp
void taskA() {
    doSomething();
}

void taskB() {
    doSomethingElse();
}
```

如果直接调用：

```cpp
int main() {
    taskA();
    taskB();
}
```

同一条线程先执行 `taskA()`，返回后执行 `taskB()`。

如果创建两个线程：

```cpp
#include <thread>

int main() {
    std::thread t1(taskA);
    std::thread t2(taskB);

    t1.join();
    t2.join();
}
```

此时 `taskA` 和 `taskB` 可以在不同线程中推进。

注意：创建两个线程不意味着它们一定在两个 CPU 核心上同时运行。这要涉及并发和并行。

## 三、并发（Concurrency）与并行（Parallelism）

这是整套概念中最重要的区别之一。

### 3.1 并发：多个任务在同一段时间内推进

假设有两个任务：

- 任务 A：计算一个几何模型。
- 任务 B：读取一个文件。

即使只有一个 CPU 核心，也可以通过任务切换来推进它们。

单核心上的并发

示意图：任意时刻只有一个任务占用 CPU，但两个任务交替推进。

这种情况属于并发，但不属于并行。

### 3.2 并行：多个任务在同一时刻实际执行

假设计算机有两个 CPU 核心：

双核心上的并行

两个任务在相同的时间区间内，分别占用不同的计算核心。

区别可以概括为：

|        | 并发            | 并行                  |
| ------ | ------------- | ------------------- |
| 英文     | Concurrency   | Parallelism         |
| 关键特征   | 多个任务的执行在时间上重叠 | 多个计算在同一时刻实际执行       |
| 必须多核心？ | 否             | CPU 任务级并行通常需要多个执行单元 |
| 必须多线程？ | 否             | 否，GPU、SIMD、多进程也可实现  |

并发是一种任务组织与推进方式，并行是一种实际执行状态。

需要注意：广义的并行还包括 GPU 数据并行、CPU SIMD 向量化等，不局限于多个操作系统线程。

## 四、同步（Synchronous）与异步（Asynchronous）

这里需要先明确语境。

在 API 和 I/O 编程中，同步与异步通常描述：操作的完成如何与调用者的后续执行关联。

### 4.1 同步操作

假设读取一个文件。

```cpp
auto data = readFile("data.txt");

process(data);
```

这里的 `readFile` 假定为同步读取 API。

调用 `readFile` 后，在成功返回时，读取操作已经完成，并返回结果。

然后才能使用读取结果执行 `process`。

同步调用的时间线

注意，这里只说明同步调用必须在返回时给出其调用结果（包括成功、错误或者暂时不可用）。

同步不一定意味着线程阻塞。 这点下一章会展开。

### 4.2 异步操作

假设存在这样的接口：

```cpp
asyncReadFile("data.txt", [](Data data) {
    process(data);
});

doOtherWork();
```

这是示意代码，并非标准库 API。

执行流程如下：

1. 发起文件读取请求。
2. `asyncReadFile` 在文件读取完成之前就可以返回。
3. 调用者继续执行 `doOtherWork`。
4. 当读取操作完成时，运行时通过回调交付结果。

异步调用的时间线

示意图：I/O 操作与调用者的其他工作发生时间重叠。

异步编程不一定需要回调，还可以使用：

- Future / Promise
- Coroutine + `co_await`
- Event Loop
- Event Loop、Future / Promise 和完成回调

这些是不同的异步结果表示或交付方式。

### 4.3 关键区别

同步：操作的完成与当前调用的返回绑定。

异步：发起操作与最终完成可以分离，结果稍后交付。

这并不直接告诉我们执行了多少线程，也不直接说明线程是否阻塞。

另外，synchronization 还有另一种常见含义：线程之间的同步协调。例如 mutex、condition variable、semaphore、barrier。它与这里的同步/异步 API 是不同的概念，尽管两者相关。

## 五、阻塞（Blocking）与非阻塞（Non-blocking）

这组概念主要关注：当前线程在等待某个事件时能不能继续执行其他工作。

### 5.1 阻塞

例如：

```cpp
auto data = blockingRead();
```

假设读取数据需要等待磁盘或网络 I/O。

调用期间，当前线程可能被操作系统挂起，暂时不能执行其后面的代码。

但要注意：

线程阻塞不等于 CPU 被占用。

操作系统可以把 CPU 分配给其他可运行线程。

这与忙等（Busy Waiting）不同。

忙等可能是：

```cpp
while (!isReady()) {
    // 不断检查
}
```

这种代码会持续执行循环并消耗 CPU 时间，虽然没有被操作系统挂起，但仍然无法继续处理后续逻辑。

### 5.2 非阻塞

以 POSIX Socket 为例：

```cpp
ssize_t n = recv(fd, buffer, size, MSG_DONTWAIT);
```

设置非阻塞接收后：

- 如果有数据，立即返回已读取的数据量。
- 如果当前没有数据可读，则可能返回 `-1`，并设置 `errno` 为 `EAGAIN` 或 `EWOULDBLOCK`。
- 不会为了等待数据到达而让这次调用一直停住。

因此，非阻塞不意味着操作已经成功完成。

它只意味着：这次调用不会为了等待相关条件满足而一直阻塞。

此外，在并发算法领域，non-blocking 也有更严格的含义，例如 lock-free 和 wait-free。这些是关于算法进展保证的术语，不能直接等同于非阻塞 I/O。

## 六、同步/异步与阻塞/非阻塞：四种组合

这是最值得深入理解的部分。

|    | 阻塞            | 非阻塞             |
| -- | ------------- | --------------- |
| 同步 | 同步阻塞 I/O      | 同步非阻塞 I/O       |
| 异步 | 发起异步操作后阻塞等待结果 | 发起异步操作，稍后接收完成通知 |

逐一解释。

### 6.1 同步 + 阻塞

最传统的方式。

```cpp
auto data = blockingRead();
process(data);
```

读取操作完成之前，当前线程无法继续执行 `process`。

### 6.2 同步 + 非阻塞

例如，通过非阻塞 Socket 反复尝试读取。

```cpp
while (true) {
    auto result = tryRead();

    if (result.hasData()) {
        process(result.data());
        break;
    }

    doOtherWork();
}
```

假设 `tryRead()` 是一次同步、非阻塞的读取尝试：

- 每次调用都会立即返回本次尝试的结果。
- 如果没有数据，就报告暂时不可用。
- 当前线程可以继续执行其他代码。
- 程序可以选择之后再次尝试。

重点是：每次调用自身是同步完成的，而不是登记一个以后交付结果的异步请求。

这就是同步和非阻塞并不矛盾的原因。

### 6.3 异步 + 阻塞

例如：

```cpp
auto future = startAsyncTask();

auto result = future.get();
```

假设 `startAsyncTask()` 确实启动了异步操作。

任务本身是异步启动的，但是紧接着调用 `get()`，当前线程会阻塞，直到结果可用。

所以：

- 操作的执行方式是异步的。
- 调用者等待结果的行为是阻塞的。

这是经常被忽略的一种组合。

### 6.4 异步 + 非阻塞

例如：

```cpp
asyncRead([](Data data) {
    process(data);
});

doOtherWork();
```

发起操作以后，调用者不需要停下来等。

等操作完成后，再通过回调或者其他完成机制处理结果。

这种组合是现代高性能 I/O 系统常见的设计。

不过要区分：调用线程非阻塞，不代表整个系统没有其他线程阻塞。异步库内部可能使用工作线程执行阻塞式 I/O。

## 七、任务时间线与事件循环交互

前面的术语分别描述了执行资源、时间关系、完成语义、等待行为和控制流。下面的实验把这些维度放在同一个确定性模型中。时间线视图允许自由编辑任务和线程数；事件循环视图则只使用一条逻辑线程，逐步观察协程如何进入等待、恢复和完成状态。

<ConcurrencyExecutionModelDemo client:visible />

时间线中的计算区段会占用执行资源，阻塞等待继续占用线程，非阻塞等待则释放线程。两个任务的生命周期重叠时，摘要会标记为并发；只有不同线程轨道上的计算区段在时间上重叠，才会标记为任务级并行。

事件循环视图不创建真实操作系统线程。它用 <code>ready → running → waiting → resumed → done</code> 这条状态链模拟单线程协程调度，从而把“协程可以并发推进”和“同一时刻只有一条线程执行指令”同时展示出来。

## 八、协程（Coroutine）是什么？

到这里，已经有足够的基础来理解协程了。

协程不是线程，而是一种可以挂起（Suspend）并在之后恢复（Resume）的执行过程。

普通函数大致是：

```cpp
void task() {
    step1();
    step2();
    step3();
}
```

调用 `task()` 以后，会按照正常控制流执行，直到返回或者抛出异常。

而协程可以在执行到一半时挂起。

以 C++20 协程语法为例：

```cpp
Task task() {
    step1();

    co_await something();

    step2();
}
```

这里的 `Task` 和 `something()` 代表某个具体协程库提供的类型与 Awaitable。

`co_await` 在 Awaitable 允许且要求挂起时，可以使协程暂停。

暂停时，协程可以保留：

- 局部变量等协程状态
- 恢复位置
- 后续执行所需的信息

等到满足恢复条件时，再从挂起位置继续运行。

注意：`co_await` 不一定真的挂起。如果所等待的操作已经就绪，协程可能直接继续执行。

### 8.1 为什么单线程也可以运行多个协程？

假设只有一条线程，但有两个协程 A 和 B。

单线程上的协程交替执行

实色表示运行，虚线表示暂停。两个协程使用同一条线程，交替获得执行机会。

过程可能是：

1. 线程运行协程 A。
2. A 发起 I/O，随后挂起。
3. 线程运行协程 B。
4. B 也可以挂起。
5. A 的 I/O 完成，运行时恢复 A。
6. B 的等待条件满足后，再恢复 B。

在这个例子中，A 和 B 实现了并发，但没有在 CPU 上同时执行，因此没有任务级并行。

### 8.2 协程与线程有什么本质不同？

| 对比         | 线程          | 协程              |
| ---------- | ----------- | --------------- |
| 本质         | 操作系统调度的执行流  | 可以暂停与恢复的执行过程    |
| 是否自带操作系统线程 | 是           | 否               |
| 能否挂起       | 可以          | 可以              |
| 谁负责调度      | 通常由操作系统调度   | 由程序或运行时控制恢复     |
| 是否天然并行     | 否           | 否               |
| 是否自动异步     | 否           | 否               |
| 常见应用       | 并行计算、独立工作线程 | 异步 I/O、任务编排、状态机 |

特别需要注意 C++20：

C++ 协程语言机制本身不提供线程池、不提供事件循环，也不提供通用的异步 I/O 实现。

它提供的是协程挂起、恢复以及相关状态管理机制。

某个协程是否跨线程恢复，取决于具体的 Awaitable、Scheduler 和运行时设计。

因此，一个协程完全可以一直运行在同一条线程中，也可以在挂起后被另一个线程恢复。

## 九、抢占式（Preemptive）与协作式（Cooperative）调度

这个概念可以帮助你进一步理解线程和协程之间的区别。

抢占式调度：调度器可以在任务没有主动让出执行权的情况下，暂停它并切换到其他任务。

操作系统线程通常采用抢占式调度。

协作式调度：任务通常需要主动挂起或让出执行权，调度器才有机会执行另一个任务。

许多协程调度系统使用这种方式。

例如：

```cpp
Task A() {
    while (true) {
        compute();
    }

    co_return;
}
```

假如 `compute()` 从不返回、不挂起、也没有其他调度机制介入，那么在单线程协作式调度器中，其他协程就可能一直没有机会运行。

所以：

> 协程让控制流可以主动挂起，并不意味着协程运行时会自动公平地调度所有任务。

操作系统仍可能抢占运行这个协程的底层线程，但这不等于协程运行时会自动切换到另一个协程。

## 十、用一个例子统一全部概念

假设有两个任务：

- A：从网络下载文件。
- B：计算一个几何模型。

看看不同实现有什么区别。

方案 1：单线程 + 同步 + 阻塞

```cpp
auto file = blockingDownload();
auto model = computeGeometry();
```

下载完成以后才开始计算，两个任务顺序推进。

方案 2：多线程 + 同步 + 阻塞

```cpp
std::thread t1([] {
    blockingDownload();
});

std::thread t2([] {
    computeGeometry();
});

t1.join();
t2.join();
```

下载和计算可并发推进。如果计算线程有独立的 CPU 资源，还可以与其他 CPU 工作并行。主线程在 `join()` 处等待。

方案 3：单线程 + 异步 + 非阻塞

```cpp
asyncDownload([](File file) {
    processFile(file);
});

computeGeometry();
```

假设异步下载由真正的非阻塞 I/O 运行时支持，那么下载期间可以执行几何计算。但下载完成的回调也需要运行时获得执行机会。

方案 4：单线程 + 协程 + 异步

```cpp
Task downloadTask() {
    auto file = co_await asyncDownload();
    processFile(file);
}
```

等待下载期间协程可以挂起，让同一线程运行别的任务。这里仍然需要一个能够驱动异步操作和恢复协程的运行时。

这四种方案可以完成类似的业务目标，但其执行机制完全不同。

## 十二、共享、通信与正确性

执行模型只说明任务如何推进，并不能自动保证结果正确。多个任务之间还需要明确数据交换方式：

- 共享内存需要 mutex、读写锁、原子操作或其他同步原语；
- 消息传递需要 channel、队列或事件；
- 无锁算法需要单独分析原子性、进展保证和内存序；
- 事件循环和协程避免了部分线程切换成本，但仍然要处理共享状态和取消；
- 内存可见性决定一个线程写入的数据何时能被另一个线程可靠观察。

因此，看到“多线程”“异步”或“协程”时，不能直接推出程序是安全的。执行资源、调度方式和数据同步必须一起分析。

## 十三、最终判断清单

遇到一个陌生的并发 API 时，可以按下面顺序判断：

1. 谁实际执行指令：一条线程、多条线程、进程，还是 GPU 队列？
2. 多个任务的生命周期是否重叠？
3. 是否有不同执行资源在同一时间实际运行？
4. 调用者是否必须等待结果？
5. 等待期间当前执行资源是否还能推进其他任务？
6. 执行过程能否保存状态并从中途恢复？
7. 任务由谁切换：操作系统、事件循环，还是协作式运行时？
8. 数据通过共享内存还是消息传递交换？
9. 锁、原子操作、Future、事件或其他同步点在哪里建立？
10. 结论描述的是逻辑并发，还是已经由硬件观测到的物理并行？

<strong>把这些问题分别回答，就不会再把“异步”“非阻塞”“多线程”“协程”“并发”和“并行”当成同一个概念。</strong>
