假设正在编写一个图形学工具：任务 A 从网络下载资源文件，任务 B 计算另一个几何模型，两者之间没有数据依赖。最直接的实现是先下载、再计算；但如果下载花了几秒钟，明明可以提前开始的几何计算也只能等在那里。当下载数量变成几百、几千个时，怎样安排执行和等待，就成了一个需要认真设计的问题。

本文以 Linux 用户态程序为背景，沿着“一个等待拖住后续工作 → 多线程与线程池 → 区分计算和等待瓶颈 → 非阻塞 I/O 与事件循环 → 异步结果与协程”的顺序推进，再用 Node.js 对照这些概念如何组合。这个顺序按问题展开，不是严格的发明年代顺序，也不是一条必须逐项替换旧方案的升级路线。

阅读时先分开三个问题：<strong>谁在执行，等待时占住了什么资源，以及我们希望改善什么。</strong>减少一次计算的完成耗时、让其他任务及时获得执行机会、让少量线程管理大量等待，是不同的目标；理解它们，才能判断每种执行机制解决了哪一部分问题。

正文中的 `blockingDownload`、`computeGeometry`、`asyncDownload` 等函数是说明流程的示意接口；协程部分先用 Rust 的 `async` / `await` 解释可挂起的控制流，再对照 Go 与 Node.js 的运行方式。文中的代码执行器另有可以直接运行的完整示例。

## 一、单线程顺序执行：为什么下载拖住了计算？

### 1.1 先确定谁在执行代码

程序（Program）是存储在磁盘上的代码与相关数据；进程（Process）是程序运行时形成的执行环境，拥有虚拟地址空间等资源，包含一条或多条线程；线程（Thread）则是其中实际推进代码的执行流。同一进程的线程通常共享堆内存等资源，但各自保有调用栈、寄存器状态和执行位置，可以执行到不同的位置。

Linux 为每个线程维护一个 `task_struct`，以 task 为基本可调度任务，把可运行线程安排到逻辑 CPU 上执行。<strong>对于用户态程序，Linux 具体调度的是进程中的各个线程。</strong>单线程进程通过其唯一的线程推进代码，多线程进程中的线程则可以分别获得执行机会。[Linux 调度文档](https://man7.org/linux/man-pages/man7/sched.7.html)也以线程为调度策略与优先级的控制对象。

本文中的“线程”默认指用户态程序的线程。Linux 语境中的“内核线程”通常特指执行内核代码的线程，不能因为用户态线程受内核调度就这样称呼它。后文的协程由程序侧代码或运行时管理，真正执行时也需要线程承载。先从只有一条线程的顺序调用开始。

### 1.2 同步阻塞调用把后续工作留在原地

```cpp
auto file = blockingDownload();
processFile(file);
auto model = computeGeometry();
```

这里假设 `blockingDownload()` 是同步、阻塞的下载接口：成功返回时，文件已经下载完成，调用者可以立即使用结果。如果网络数据尚未到达，调用线程可以进入内核等待；下载没有结束，后面的文件处理与几何计算就都无法执行。

这个例子中，“返回时交付结果”与“等待时线程停住”同时出现，分别属于同步语义和阻塞行为。先记住它们回答的是两个问题；第五节会结合非阻塞调用和异步结果，统一比较四种组合。

线程进入等待不等于 CPU 被它占用。Linux 可以把 CPU 分配给其他可运行线程，但当前程序只有这一条线程，所以独立的几何计算仍然不会自动开始。即使改成循环检查下载是否结束，后续逻辑也不会自己获得执行机会：

```cpp
while (!isReady()) {
    // 不断检查
}
```

这种忙等（Busy Waiting）会持续消耗 CPU 时间，没有因等待条件而进入内核睡眠状态，仍然可以被 Linux 抢占，却没有解决当前调用链无法前进的问题。既然下载和几何计算没有依赖，一个直接的改进就是把它们交给不同线程。

## 二、创建多个线程：让独立任务分别推进

### 2.1 多一条执行流，等待就不必挡住所有工作

```cpp
#include <thread>

int main() {
    std::thread t1([] {
        auto file = blockingDownload();
        processFile(file);
    });

    std::thread t2([] {
        computeGeometry();
    });

    t1.join();
    t2.join();
}
```

下载线程等待数据时，几何计算线程仍可以获得 CPU 执行机会，主线程则在 `join()` 处等待工作线程结束。这已经解决了“一个下载阻塞整条业务调用链”的问题，但创建两个线程不意味着它们一定在两个核心上同时运行；还要区分任务的并发与并行。

### 2.2 并发不要求同时执行，并行才要求

先考虑不启用同时多线程（SMT）的单核心情况：Linux 可以交替调度下载线程和计算线程，下载线程等待 I/O 时也可以继续执行计算线程。两个任务在同一段时间内推进、生命周期发生重叠，构成并发（Concurrency）；但任意时刻只有一条线程在该核心上执行指令，没有 CPU 上的任务级并行。

如果有两个可用核心，而且两条线程都处于可运行状态，它们就有机会分别在不同核心上同时执行，构成并行（Parallelism）。不过，正在阻塞等待网络的线程并没有在 CPU 上计算，不能把“下载等待与几何计算重叠”直接当作两条线程的 CPU 并行。

并发与并行的区别可以概括为：

|        | 并发            | 并行                  |
| ------ | ------------- | ------------------- |
| 英文     | Concurrency   | Parallelism         |
| 关键特征   | 多个任务的执行在时间上重叠 | 多个计算在同一时刻实际执行       |
| 必须多核心？ | 否             | CPU 任务级并行通常需要多个执行单元 |
| 必须在同一进程内使用多线程？ | 否             | 否，多个单线程进程、GPU 或 SIMD 也可实现  |

这个区别也适用于其他执行资源：多个单线程进程可以通过各自的线程在不同 CPU 核心上并行执行，广义的并行还包括 GPU 数据并行、CPU SIMD 向量化等。接下来先限定在 Linux 线程与逻辑 CPU 的关系上做实验。

下面的实验把线程数量与可用逻辑 CPU 数量分开。先在 1 CPU 与 2 CPU 的预设之间切换，观察同一时刻能执行几条线程；再尝试 4 CPU／10 线程，看看其余线程如何在就绪队列中等待执行机会。每条线程固定需要 4 tick 计算，使用 1 tick 时间片轮转，竖线处的当前状态与整段执行过程的结论分别显示。

### 2.3 线程超过核心数，就只有并发了吗？

假设程序可以使用 4 个物理核心、不启用 SMT，并且有 10 个线程都处于可运行状态，持续执行 CPU 计算。同一时刻，最多有 4 个线程在这些核心上执行，其余线程等待调度；随着执行机会的轮换，10 个线程都可以在一段时间内推进。这里既有全部线程在时间上的并发，也可以有其中 4 个线程的并行。<strong>线程超过核心数，只意味着无法让所有线程同时执行，并不会让已有的并行消失。</strong>

实际分析时，还要区分物理核心与逻辑处理器。启用 SMT 后，一个物理核心可以提供多个硬件线程上下文，让 Linux 将不同软件线程调度到对应的逻辑处理器上；它们可以同时推进，但共享核心的部分执行资源，不能直接当作同等数量的独立物理核心。[Intel 对超线程的说明](https://www.intel.com/content/www/us/en/gaming/resources/hyper-threading.html)介绍了这种区别。

此外，线程总数并不等于当前争用 CPU 的线程数。正在等待 I/O 或其他事件的线程通常不在可运行队列中；判断并行程度时，应看当前可运行的线程、实际可用的逻辑处理器，以及它们是否真的同时执行。

## 三、线程池：复用线程，让任务排队执行

### 3.1 从“每个任务创建线程”到“任务交给工作线程”

两个独立任务可以各用一条线程，但如果每个下载、每个小计算都创建新线程，任务越多，线程的创建、销毁、栈内存和调度管理成本也越多。任务生命周期很短时，反复创建线程尤其不划算；无限制地增加线程，也不能无限增加实际可用的 CPU 资源。

线程池把任务与承载它们的线程分开：程序维护一组长期存在的工作线程，提交的任务先进入队列，再由可用的工作线程取出执行。一个任务完成后，线程可以继续执行下一个任务。下面用 [Boost.Asio 的固定大小线程池](https://www.boost.org/doc/libs/latest/doc/html/boost_asio/reference/thread_pool.html)表达这个结构，下载和计算函数仍是前面的示意接口：

```cpp
#include <boost/asio/post.hpp>
#include <boost/asio/thread_pool.hpp>

boost::asio::thread_pool pool(4);

boost::asio::post(pool, [] {
    auto file = blockingDownload();
    processFile(file);
});

boost::asio::post(pool, [] {
    computeGeometry();
});

pool.join();
```

这里最多由池中的 4 条工作线程同时执行已提交的任务，主线程在 `pool.join()` 处等待。任务数量可以大于线程数量，因为尚未执行的任务可以排队，而不必各自拥有一条线程。任务队列由线程池管理，工作线程何时获得 CPU 则仍由 Linux 内核调度。

### 3.2 线程池没有消除阻塞等待

如果 4 条工作线程都进入 `blockingDownload()` 等待网络，第 5 个已经排队的任务仍然无法执行。即使它只是一个很短的计算，也必须等某条工作线程空闲。线程池复用了线程、控制了工作线程数量，却没有改变池中任务调用阻塞函数时的行为。

可以根据任务性质调整工作线程数量，或者将计算任务和阻塞 I/O 任务交给不同的池，但大量等待依然需要占住工作线程。另外，固定工作线程数量也不等于限制排队任务数量；任务提交速度持续超过处理速度时，还需要队列容量或其他流量控制策略。要进一步选择执行方式，需要先判断任务的时间主要花在计算，还是等待 I/O 上。

### 3.3 任务是在计算，还是在等待 I/O？

几何计算、图像解码等工作如果主要受计算能力限制，通常称为计算密集型（CPU-bound）；下载、文件读写等工作如果主要受 I/O 吞吐或等待延迟限制，通常称为 I/O 密集型（I/O-bound）。这描述的是当前场景下的主要瓶颈，不是固定不变的任务类别：同一个流程可以先等待下载，再进行解码计算，随后等待写入，数据规模、硬件与实现方式也可能改变它的瓶颈。

除了判断整体瓶颈，还要看任务当前处于哪个阶段，以及这个阶段占用了哪些执行资源：

| 当前阶段 | 是否占用承载任务的工作线程 | 是否使用 CPU 推进任务 |
| ---- | ---- | ---- |
| 持续计算，尚未交还控制权 | 是 | 获得 CPU 时执行计算 |
| 线程阻塞等待 I/O | 是，线程停在当前任务的调用中 | 等待期间不执行任务计算 |
| 任务挂起等待 I/O | 否，线程可以执行其他就绪任务 | 当前任务挂起期间不执行计算 |

这里区分的是任务的计算与等待阶段，并不是说整个 I/O 操作不消耗 CPU。准备缓冲区、处理协议、复制数据和完成后的业务处理都可能需要计算；“任务挂起”则表示先保存进度并交还控制权，后文会用协程说明它如何恢复。表格也只描述承载当前任务的工作线程，真实库内部仍可能有其他线程负责 I/O。

<strong>持续计算与阻塞等待都可能让工作线程暂时无法处理其他任务，但线程状态不同。</strong>计算线程可能正在 CPU 上执行，也可能处于就绪状态等待 CPU；真正阻塞等待 I/O 的线程则要等相应条件满足后才能再次运行。Linux 可以抢占正在计算的线程，把 CPU 交给其他线程，却不会因此替用户态运行时切换到这条线程上的另一个任务。因此，长计算占住事件循环时常被称为“阻塞事件循环”，这不等于线程已经进入内核阻塞等待状态。

由此还不能直接得出“该增加线程”或“该使用异步”的结论。下一步要明确，想改善的是单个任务的完成耗时、其他任务的响应，还是等待期间的资源利用率。

### 3.4 缩短计算、改善响应与管理等待，是三个目标

假设几何任务本身需要累计约 100 ms 的 CPU 计算时间。只把函数改写为 `async`，不会自动减少这些计算；在同一条线程上执行，它仍需要获得相应的 CPU 时间。如果想利用多个 CPU 缩短完成耗时，就要找到可以独立推进的工作，由多条线程等执行资源同时处理，再合并结果。数据依赖、通信与同步成本会影响收益，不能仅凭线程数推断加速比例。

如果把这 100 ms 的计算分成十批，每批约 10 ms，批次之间交还执行权，主要改善的则是<strong>响应性</strong>：事件循环有机会在批次之间处理新事件或其他任务，不必一直等这段计算全部结束。计算总量没有因此减少，额外的调度管理还可能增加完成耗时。这种安排解决的是其他任务多久能获得执行机会，与多核同时计算的目标不同；第六节会用主动让出的例子展示它。

对于下载任务，假设网络传输本身需要约 5 秒，改成异步等待不会自动把传输缩短成 1 秒。收益在于，等待这 5 秒时不必让承载任务的工作线程一直停在调用中，而可以让它处理其他连接或计算。多个请求因此可能更少地排队等待线程，系统也可以用少量线程管理更多等待中的任务；最终吞吐仍受网络、设备和后续计算等资源限制。

回到开头的两个任务：几何计算可以按计算资源和响应要求安排，下载则需要选择合适的等待方式，两者并不要求使用同一种机制。后面的非阻塞 I/O 先解决等待占住线程的问题，异步结果与协程再解决任务如何在等待前后接续；最后回到这些机制如何组合。先聚焦等待：网络数据尚未到达时，能不能把线程腾出来执行别的任务？

## 四、非阻塞 I/O 与事件循环：让等待不再独占线程

### 4.1 没有数据时，先返回本次尝试的结果

以 Linux Socket 接收为例，调用时使用 `MSG_DONTWAIT`，可以让本次接收不为了等待数据到达而停住：

```cpp
ssize_t n = recv(fd, buffer, size, MSG_DONTWAIT);
```

如果有数据可读，这次调用会返回已读取的数据量；如果当前没有数据可读，则可能返回 `-1`，并设置 `errno` 为 `EAGAIN` 或 `EWOULDBLOCK`。非阻塞不保证读取成功，它只改变“条件尚未满足时如何等待”：调用者拿到本次尝试的结果后，可以继续执行其他代码。

用示意接口表示，程序可以先尝试读取，没有数据就处理其他工作，之后再试：

```cpp
while (true) {
    auto result = tryRead();

    if (result.hasData()) {
        process(result.data());
        break;
    }

    doOtherWork();
}
```

这里的 `tryRead()` 是同步、非阻塞的读取尝试，每次调用都在返回时交付本次尝试的结果，没有登记一个稍后交付最终结果的异步请求。这说明同步与非阻塞可以同时成立。不过，如果没有多少其他工作可做，或者需要反复检查成千上万个连接，这种循环仍可能浪费 CPU；还需要一种办法，在连接值得再次尝试时收到通知。

### 4.2 通过事件通知，把线程交给已就绪的工作

Linux 的 [`epoll`](https://www.man7.org/linux/man-pages/man7/epoll.7.html)可以监视多个文件描述符的 I/O 就绪事件。以非阻塞网络读取为例，程序先登记关注的连接，事件循环取得可读事件后再尝试接收；如果一次只能读到部分数据，就保存下载进度，之后继续处理这个连接或其他连接。

这里的就绪通知只表示可以尝试相应 I/O，并不等于整个文件已经下载完成；实际读到的数据量、连接是否关闭以及错误情况，仍要检查读取结果。事件循环也不是下载操作本身，而是反复处理就绪事件、调用对应处理逻辑的一种程序组织方式。

当没有就绪任务需要处理时，事件循环可以通过 [`epoll_wait()`](https://man7.org/linux/man-pages/man2/epoll_wait.2.html)进入内核等待，有事件到来后再继续工作。因此，“使用非阻塞 I/O”不意味着整个系统没有线程阻塞。变化在于，一条线程可以统一等待多个连接的事件，而不必为每个等待中的连接各占一条线程；`epoll` 本身也不会自动创建工作线程或恢复协程。

此外，non-blocking 在并发算法领域还有更严格的语境，例如 lock-free 和 wait-free，讨论的是算法的进展保证，不能直接等同于这里的非阻塞 I/O。

## 五、异步结果：操作尚未完成，后续工作如何接上？

### 5.1 用回调接续下载后的处理

底层可以通过非阻塞读取和事件通知推进下载，但业务代码通常更希望表达“发起下载，完成后处理文件”。库可以把连接、缓冲区和下载进度封装起来，对外提供一个异步接口：调用时登记后续处理，下载完成后再交付最终结果。

```cpp
asyncDownload([](File file) {
    processFile(file);
});

computeGeometry();
```

这里假设 `asyncDownload()` 登记请求后即可返回，运行时通过非阻塞 I/O 推进下载，并在完成后调用回调。调用者可以继续进行几何计算，而不必等到文件下载结束。示例只写出了成功路径；完整接口还需要定义失败如何交付，以及请求取消后如何处理。

这就是异步（Asynchronous）完成语义：发起操作与最终交付结果可以分离。前面的同步（Synchronous）调用则在当前调用返回时交付本次操作的结果，结果可能是数据、错误，也可能是“暂时不可用”。<strong>同步与异步描述完成语义，阻塞与非阻塞描述等待行为。</strong>底层使用事件通知，并不意味着每个读取调用本身都是异步 API。

### 5.2 用 Future / Promise 表示尚未完成的结果

回调需要调用者提供一段“完成后执行什么”的逻辑，Future / Promise 则提供一个对象来表示尚未取得的结果。在一些库中，Promise 一侧负责发布结果或错误，Future 一侧供调用者取得结果；具体语言如何实现和驱动它们并不相同。它们本身不等于线程，不能仅凭类型名称推断底层用了事件循环还是工作线程；第六、七节会分别对照 Rust Future 与 JavaScript Promise。

取得 Future 后，调用者仍然可能选择阻塞等待。例如，假设下面的示意函数确实启动了异步下载，并返回类似 `std::future` 的对象：

```cpp
auto future = startAsyncDownload();
auto model = computeGeometry();
auto file = future.get();
processFile(file);
```

几何计算可以与下载等待重叠；但如果执行到 `get()` 时结果仍未就绪，当前线程仍会阻塞，直到能够取得结果。操作异步启动，并不保证调用者之后采用的每一种等待方式都是非阻塞的。

### 5.3 回看四种组合，区分操作与等待

到这里，四种组合都可以用已经遇到的机制解释，不需要把“同步”与“阻塞”绑定成一个概念。其中，“异步 + 阻塞”描述的是发起异步操作、再阻塞等待结果的组合过程。

| 完成语义与等待行为 | 已经遇到的例子 | 调用者如何继续 |
| ---- | ---- | ---- |
| 同步 + 阻塞 | `blockingDownload()` | 等待下载结束，再取得结果并执行后续代码 |
| 同步 + 非阻塞 | `tryRead()` 或非阻塞 `recv()` | 取得本次尝试的结果，没有数据时可以先做其他工作 |
| 异步 + 阻塞 | 发起下载后调用 `future.get()` | 任务已经异步启动，但结果未就绪时当前线程仍会等待 |
| 异步 + 非阻塞 | 登记异步下载，稍后通过完成回调接收文件 | 等待期间线程可以推进其他任务 |

表中的等待行为描述调用者这一侧。某些异步接口内部会把普通阻塞 I/O 转交给工作线程，再通知调用者结果；这一层资源安排需要继续追踪，不能从接口的完成语义直接推断。

回调和 Future 已经能把下载与计算组织起来，但业务一旦变成“下载、校验、解码，再处理结果”，后续逻辑就可能分散在多个回调或手写状态之间。能不能保留从上到下的书写顺序，同时让每一步等待都释放当前线程的执行机会？这就是引入协程的动机。

## 六、协程：让可挂起的任务保持连贯控制流

### 6.1 将等待写进流程，而不占住线程

协程（Coroutine）是一种可以挂起（Suspend）并在之后恢复（Resume）的执行过程。普通函数通常沿调用链执行到返回或抛出异常，协程则可以在中途保存状态，把控制权交还给调用者或运行时。以 Rust 的 `async` / `await` 语法表达下载后的处理：

```rust
async fn download_task() {
    let file = async_download().await;
    process_file(file);
}
```

这里的 `async_download()` 和 `process_file()` 是由应用或库提供的示意接口。调用 `download_task()` 先返回 Future，执行器轮询它才会推进函数体。代码从上到下表达“取得文件，再处理文件”，下载等待则通过挂起当前任务处理。

`.await` 轮询的 Future 返回 `Pending` 时，当前异步任务挂起并交还控制权；满足唤醒条件后，执行器可以再次轮询，使任务从等待处继续推进。如果 Future 已经返回 `Ready`，则直接继续执行，<strong>无需挂起</strong>。<strong>协程提供保存状态、挂起与恢复的控制流能力，本身不提供线程、事件循环或通用异步 I/O。</strong>从更一般的协程概念看，协程也可以用于同步的生成过程，不能仅凭使用了协程就认定操作一定异步或并行。

### 6.2 一条线程如何推进多个任务

如果下载协程与其他任务由同一个事件循环驱动，运行过程可以是：

1. 线程开始执行下载协程，发起异步下载。
2. 下载暂未完成，协程保存状态并挂起，把控制权交还运行时。
3. 运行时让同一线程执行已就绪的几何计算任务或其他协程。
4. 计算任务返回或让出执行权后，事件循环继续处理网络事件。
5. 下载完成，运行时恢复下载协程，继续执行文件处理。

这正是第二节讨论的<strong>单线程并发</strong>：任务交叠推进，没有 CPU 上的任务级并行。网络条件就绪也只表示具备继续处理的条件，回调或协程仍要等执行机会；如果几何计算长时间不返回或不交还控制权，下载完成后的处理也会延迟。线程与协程分别位于不同的执行安排层次：

| 对比 | 线程 | 协程 |
| ---- | ---- | ---- |
| 本质 | Linux 内核可调度的执行流 | 可以挂起与恢复的执行过程 |
| 执行资源 | 获得逻辑 CPU 上的执行机会 | 需要由某条线程承载 |
| 谁安排执行 | Linux 内核调度器 | 程序、事件循环或运行时 |
| 状态如何保留 | 线程有自己的调用栈与寄存器上下文 | 取决于状态机或栈切换等实现方式 |
| 是否天然并行 | 否，取决于实际调度与硬件资源 | 否，还取决于承载它的线程与运行时 |
| 常见用途 | 并行计算、独立工作线程 | 异步任务编排、生成过程、状态管理 |

### 6.3 如何实现，一定需要协程调度器吗？

程序侧实现和管理协程，并不要求开发者手写整套机制，其中也包括编译器生成的代码、库和语言运行时。Rust 与 Go 展示了两种不同的状态保存与执行安排。

Rust 的 `async fn` 体现了无栈协程的实现方式：编译器将异步函数转换成实现 `Future` 的状态机，把跨越挂起点仍需保留的局部变量和执行进度保存在 Future 中。轮询时，函数代码使用当前线程的调用栈执行；挂起时则由 Future 保存接续所需的状态，无需为每个异步任务保留一条独立的完整调用栈。<strong>“无栈”指的是挂起状态的保存方式，不意味着执行时不使用线程的调用栈。</strong>[Tokio 的异步机制教程](https://tokio.rs/tokio/tutorial/async)展示了异步函数如何转换成状态机。

Tokio 提供任务调度及配套异步 I/O 等运行时能力。例如，`tokio::spawn(download_task())` 将 Future 提交为独立任务，由执行器安排轮询；返回 `Pending` 后，通过 `Waker` 收到唤醒通知的任务可以再次获得轮询机会。任务能否跨线程继续执行，还取决于 Future 是否满足 `Send` 等约束，以及执行器的调度策略。

Go 的 `go worker()` 则启动拥有可增长独立栈的 goroutine。开发者沿普通函数调用链组织流程，Go 内置运行时保存执行上下文，在需要时挂起、恢复或切换 goroutine，并把它们安排到操作系统线程上执行，无需另外选择执行器。[Go 官方 FAQ](https://go.dev/doc/faq#goroutines)说明了它的栈与线程复用机制。两种实现最终都仍由线程执行指令，再由 Linux 内核安排线程获得 CPU。

因此，<strong>保存状态、挂起与恢复的能力，不要求一定配套一套通用的协程调度器。</strong>Rust Future 不一定需要 Tokio：程序可以自行编写驱动逻辑，通过 [`Future::poll()`](https://doc.rust-lang.org/std/future/trait.Future.html#tymethod.poll) 推进尚未完成的 Future，并在返回 `Pending` 后配合 `Waker` 等待下一次轮询机会。Go goroutine 则由 Go 运行时统一调度。具体语言与库将哪些能力交给编译器、执行器或内置运行时，需要分别判断。

### 6.4 线程阻塞与协程挂起发生在不同层次

第三节已经区分了计算占用、线程阻塞等待和任务挂起等待。把普通阻塞函数放入协程，等待方式不会自动改变：条件已满足时调用可以直接返回，但确实需要等待、且运行时没有拦截或转换调用时，仍会发生线程阻塞。下表从调用位置看它影响哪些任务：

| 调用场景 | 需要等待时的行为 | 对其他任务的影响 |
| ---- | ---- | ---- |
| 单线程进程调用普通阻塞 I/O | 唯一的线程进入内核等待 | 该进程暂时无法推进自己的代码，Linux 仍可调度其他进程的线程 |
| 多线程进程中的一个线程调用普通阻塞 I/O | 调用线程进入内核等待 | 同进程中其他可运行线程仍有机会执行 |
| 协程直接调用普通阻塞 I/O，运行时未作特殊处理 | 承载该协程的底层线程进入内核等待 | 依赖该线程调度的其他协程也无法推进 |
| 协程等待与运行时配合的异步操作 | 当前协程挂起，把控制权交还给调用者或运行时 | 同一线程可以转而执行其他就绪任务 |

如果事件循环就在被阻塞的线程上，它也无法继续调度。处理时可以改用配套异步 API，或把阻塞调用交给专门的工作线程。例如，Tokio 的 [`tokio::task::spawn_blocking()`](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)在专门的线程上执行普通阻塞操作，当前异步任务通过 `.await` 等待返回的 `JoinHandle`。这保住了异步执行线程的执行机会，但承担阻塞操作的线程仍然存在。

### 6.5 长计算如何交还执行机会？

I/O 已经能够挂起等待，第三节提出的响应性问题仍然存在：连续计算期间，谁来给其他任务执行机会？Linux 用户态线程通常采用抢占式（Preemptive）调度，内核可以抢占当前线程；Tokio 异步任务则采用协作式（Cooperative）调度，需要当前任务挂起、交还控制权或执行结束，才有机会在同一线程上处理其他任务。

先用递增计数简化表示计算进度，达到目标后通过条件分支返回：

```rust
async fn geometry_task(total_steps: u64) {
    let mut step = 0;

    loop {
        if step >= total_steps {
            return;
        }

        step += 1;
    }
}
```

这个 Future 被轮询后会连续执行循环，直到 `return` 使异步函数完成。条件分支提供了结束条件，却没有提供中途交还执行权的位置；它属于计算占用，长时间执行时同样会拖延其他任务。Linux 可以抢占承载它的线程，但不会替 Tokio 在该线程上恢复另一个任务。

如果希望计算尚未完成时也能给其他任务执行机会，可以在适当位置主动让出控制权。例如，使用 Tokio 的 `yield_now().await`：

```rust
async fn geometry_task(total_steps: u64) {
    let mut step = 0;

    loop {
        if step >= total_steps {
            return;
        }

        step += 1;
        tokio::task::yield_now().await;
    }
}
```

这个版本在每步计算后主动让出，再次被轮询时从挂起处继续，局部变量 `step` 的进度也会保留。实际计算通常按适当大小分批，在批次之间让出，避免过于频繁的调度开销。[`yield_now()` 是 Tokio 提供的协作式让出接口](https://docs.rs/tokio/latest/tokio/task/fn.yield_now.html)，不是 Rust 的裸 `yield` 语法；它交还执行机会，但运行时仍可能立即再次轮询当前任务。

Go 运行时还支持 goroutine 抢占，[Go 1.14 引入的异步抢占机制](https://go.dev/doc/go1.14#runtime)使没有函数调用的循环也不再因此阻止调度。因此，这里的 Tokio 实验不能直接用于推断 Go goroutine 的行为。<strong>内核调度线程，与运行时安排用户态任务，是两个层次的执行安排；不同运行时也可能采用不同策略。</strong>

下面让 A、B 两个异步任务在 Tokio 单线程运行时中共享计数器，共同从 0 累加到 100，并统计各自完成的递增次数。`main` 中的 `should_yield_a`、`should_yield_b` 分别控制任务是否每次递增后主动让出。默认都为 `false`，先获得执行机会的任务完成全部 100 次，另一个为 0 次，但不保证 A 一定先执行。再把开关都改为 `true`，或只让一个任务让出，观察分配如何变化。

<strong>主动让出不保证严格交替，也不保证两个任务各完成 50 次。</strong>这个实验观察的是单线程上的执行机会，不是多核加速，输出也不用于测量调度性能。

`Arc` 让两个任务共享计数器的所有权，`Mutex` 保护检查与递增操作；内层作用域会在 `.await` 前释放锁。两个任务先通过 `tokio::spawn` 提交，随后依次等待两个 JoinHandle 只是收集结果，并不表示先执行完 A 才启动 B。循环中的 `break` 最终使函数返回该任务的计数、完成 Future；`yield_now().await` 则保留循环进度，等待后续继续执行。

## 七、Node.js：把接口、控制流与执行资源放在一起看

前面分别解释了线程、等待、结果交付和可挂起控制流。Node.js 提供一个可以同时对照它们的实际环境：先看文件接口，再看 JavaScript 如何保存和接续流程，最后判断执行资源的边界。

### 7.1 同一个文件，三种结果交付方式

Node.js 的同步、回调和 Promise 文件接口具有不同的完成语义和等待行为：

| 接口 | 如何取得结果 | 文件等待是否阻塞事件循环线程 |
| ---- | ---- | ---- |
| `readFileSync()`，来自 `node:fs` | 当前调用返回读取结果 | 会，调用完成前无法继续执行其他 JavaScript |
| `readFile(path, callback)`，来自 `node:fs` | 完成后执行回调 | 不会为本次文件等待占住事件循环线程 |
| `readFile()`，来自 `node:fs/promises` | 返回 Promise，可通过 `await` 接续处理 | 不会为本次文件等待占住事件循环线程 |

<strong>异步文件 API 的实现让事件循环线程不必等待文件，回调、Promise 与 async/await 则组织结果如何交付和接续。</strong>回调式异步接口已经能够在文件等待期间处理其他工作，`async/await` 并不是这项能力的来源。两个异步文件接口都使用后台线程池，承担操作的后台线程仍可能等待 I/O。[Node.js 文件系统文档](https://nodejs.org/api/fs.html)说明了这三种接口及其执行方式。

### 7.2 async/await 如何与 Rust 放进同一框架？

JavaScript 的 `async/await` 提供基于 Promise 的无栈协程式控制流，引擎保留挂起后接续所需的执行状态，Node.js 提供事件循环与 I/O 等运行时支持。在未使用 Worker 的典型程序中，这些 JavaScript 流程共享一条事件循环线程，异步函数挂起后通过 Promise 的微任务机制安排恢复；`async/await` 本身不创建线程。[V8 对异步函数的介绍](https://v8.dev/blog/fast-async)说明了这种实现与执行方式。

第三组调用 `load()` 后，函数体立即开始执行，直到 `await` 挂起或函数返回；Rust 的 `async fn` 则先返回 Future，由后续轮询推进函数体。两者都能用“保存状态、挂起、恢复”分析，但结果表示与驱动方式不同：

| 维度 | Rust + Tokio | JavaScript + Node.js |
| ---- | ---- | ---- |
| 可挂起的流程 | `async fn` 生成的 Future | `async function` 的执行过程 |
| 状态如何保存 | 保存在 Future 状态机中 | 由引擎保存异步函数的执行状态 |
| 完成结果如何表示 | Future 完成时产生 `Output` | 异步函数返回的 Promise 表示完成结果 |
| 如何继续执行 | 执行器再次轮询 Future | 引擎在微任务机制中恢复后续代码 |
| 何时开始执行函数体 | Future 被轮询时 | 调用后立即执行，直到挂起或返回 |

Rust Future 承载需要被轮询推进的计算，JavaScript 返回的 Promise 主要表示完成结果。因而，可以统一分析控制流，但不能把这两种对象或它们的启动方式直接等同。

### 7.3 async 函数里仍然可能占住事件循环

`await readFileSync(path)` 就是第六节“协程不自动改造普通调用”的一个具体例子：先求值右侧的同步读取，再进入 `await` 的挂起机制，读取期间依然阻塞事件循环。异步函数在首个挂起点前、以及恢复后执行的长计算，也要在当前线程上连续推进，不能因为函数带有 `async` 就忽略它的计算占用。

当事件循环线程执行长时间不返回的同步调用时，依赖它的请求处理、定时器回调和 Promise 后续代码都要等待。已经启动的后台任务或内核网络传输可能继续，但相应 JavaScript 处理仍要等这条线程；有限的阻塞结束后可以恢复，持续不返回的调用则会使事件循环持续失去响应。

这里的单线程范围是这组 JavaScript 流程，不是整个 Node.js 进程。除了文件等操作使用的后台线程，还可以通过 `worker_threads` 并行执行 JavaScript。[事件循环与工作线程池说明](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)和 [Worker 文档](https://nodejs.org/api/worker_threads.html)分别描述了这些资源安排。

## 八、回到整体框架：六个维度分别回答什么？

### 8.1 用六个问题描述同一个程序

前面的每一次改进，只改变了执行模型中的部分属性。现在把它们放回六个维度，作为分析一个程序的统一入口：

| 维度 | 主要概念 | 回答的问题 |
| ---- | ---- | ---- |
| 执行资源 | 单线程、多线程、GPU 队列 | 谁实际执行指令？ |
| 任务时间关系 | 并发、并行 | 任务是否交叠，是否同时运行？ |
| 完成语义 | 同步、异步 | 当前调用如何交付结果，最终结果是否稍后交付？ |
| 等待与进展 | 阻塞、非阻塞 | 当前线程是否因等待而停住？ |
| 控制流表达 | 普通函数、回调、状态机、协程 | 后续逻辑如何组织，能否保存状态并恢复？ |
| 调度权限 | 抢占式、协作式 | 谁决定何时切换执行？ |

这是一套帮助建立工程直觉的教学框架，不是严格互斥且完备的并发理论公理。数据共享、消息传递、锁、原子操作和内存可见性仍贯穿其中，后面会单独讨论正确性边界。另外，mutex、condition variable、semaphore、barrier 等语境中的 synchronization 指任务之间的同步协调，需要与同步／异步 API 的完成语义区分。

### 8.2 按目标组合机制，而不是寻找唯一替代品

回到最初的下载与几何计算任务，第三节区分的三个目标现在各有对应手段：可拆分的计算可以交给多个执行资源，响应性要求可以通过控制连续计算批次来照顾，大量等待则交给适合的 I/O 与事件机制。控制流复杂时，再用协程把等待前后的业务逻辑接起来。

| 组织方式 | 主要解决的问题 | 组合时仍需检查 |
| ---- | ---- | ---- |
| 单线程顺序调用 | 直接表达前后依赖 | 一个阻塞下载会拖住后续独立工作 |
| 多线程执行独立任务 | 一条线程等待时，其他线程仍有机会执行 | 线程成本与实际并行资源 |
| 线程池执行排队任务 | 复用线程，控制工作线程数量 | 阻塞任务占用线程，队列容量与等待 |
| 非阻塞 I/O + 事件循环 | 少量线程管理多个等待中的连接 | 保存操作进度，限制连续计算对事件处理的延迟 |
| 协程 + 异步运行时 | 连贯表达可挂起任务的后续逻辑 | 配套 I/O、执行器与调度策略 |

一种组合是让事件循环驱动下载，在任务挂起期间处理其他 I/O；把较重的几何计算提交到工作线程，完成后把结果交回业务流程。线程池里的任务仍可以采用同步阻塞调用，单线程事件循环也可以用非阻塞 I/O 与协程推进多个下载；多线程运行时则可以安排不同协程在不同逻辑 CPU 上执行，或让挂起后的任务换一条线程继续，前提是运行时和任务约束允许。

这些安排各自负责不同部分：线程池组织线程与队列，事件循环处理事件，协程组织可恢复的控制流。判断一种组合是否合适，需要把上面的维度放在一起检查，而不是用“使用了异步”代替对执行资源、等待和调度的分析。

## 十一、共享、通信与正确性

前面讨论的是任务如何推进，数据交换的正确性仍需单独分析。共享内存可以用 mutex、读写锁、原子操作等同步原语协调访问，消息传递则可以通过 channel、队列或事件完成。无论采用哪一种方式，都需要明确数据何时可以被可靠地读取和使用。

对于共享内存，内存可见性决定一个线程写入的数据何时能被另一个线程可靠观察；无锁算法还要分析原子性、进展保证和内存序。事件循环和协程即使减少了部分线程切换成本，也仍然需要处理共享状态和取消。因此，分析执行资源与调度之后，还要把数据同步纳入判断，不能只凭“多线程”“异步”或“协程”等名称认定程序安全。

## 十二、最终判断清单

遇到一个陌生的并发 API 时，可以按下面顺序判断：

1. CPU 侧由同一进程或不同进程中的哪些线程执行？是否还涉及 GPU 队列？
2. 多个任务的生命周期是否重叠？
3. 是否有不同执行资源在同一时间实际运行？
4. 当前调用交付的是本次操作的结果，还是通过独立机制在稍后交付最终结果？
5. 等待期间当前执行资源是否还能推进其他任务？
6. 执行过程能否保存状态并从中途恢复？
7. 切换发生在哪一层：Linux 内核切换线程，还是程序、事件循环或运行时切换协程？
8. 数据通过共享内存还是消息传递交换？
9. 锁、原子操作、Future、事件或其他同步点在哪里建立？
10. 结论描述的是逻辑并发，还是已经由硬件观测到的物理并行？

<strong>把这些问题分别回答，就不会再把“异步”“非阻塞”“多线程”“协程”“并发”和“并行”当成同一个概念。</strong>

关于 Rust 异步状态机与函数染色问题，可参阅[《代数效应与效应系统：从 React Suspense 到 Rust 染色函数》](/posts/type-systems/effects)。
